## Stack
Repositorio de skills Markdown para cinco harnesses — Claude Code (`claude/`), Codex (`codex/`), opencode (`opencode/`), Pi (`pi/`) y Google Antigravity (`antigravity/`) — mas extensiones TypeScript interpretadas por jiti y un Pi Package Git nativo declarado en el `package.json` raiz. Claude Code se distribuye con `.claude-plugin/`; Codex usa el marketplace `.agents/plugins/marketplace.json` y el manifest `.codex-plugin/plugin.json`, que apunta solo a `codex/`. Desde 3.0.0 (issue #103) el plugin y el package se llaman `chiche` (antes `chichex-skills`) en los tres manifests y en los dos marketplaces. El manifest de Pi es privado, ESM, sin scripts de publicacion, lockfile ni dependencias runtime; declara como peers las APIs core que Pi ya provee. Los tests usan `node:test` sobre TypeScript nativo y el gate `pi-extensions/pi-package/pi-package.test.ts` prueba inventario, carga RPC/theme, lifecycle y limpieza con configuracion descartable. Scripts de chequeo en `scripts/` y CI en `.github/workflows/ci.yml`; no hay build, `tsconfig` ni package manager local requerido. Verificado localmente con Node `v26.4.0`, Pi `0.85.1`, Bash `3.2.57`, Git `2.50.1` y GitHub CLI `2.96.0`. La extension `pi-extensions/subagent/` (tool `subagent`, comando `/subagents`, agentes bundleados `implementer`/`reviewer`/`scout`) es una adaptacion propia del ejemplo `examples/extensions/subagent` de Pi 0.85.1.

La instalacion nativa de Pi es global por defecto (`~/.pi/agent/settings.json`) y `-l` usa `.pi/settings.json`; no ejecutar ninguna contra configuracion real durante verificacion autonoma. El gate crea `HOME` y `PI_CODING_AGENT_DIR` temporales para `pi -e ./`, RPC, theme y `pi install/list/remove`, y compara la configuracion real antes/despues. El plugin de Codex se prueba con `CODEX_HOME` temporal: agregar el marketplace local, listar, instalar y revisar su cache no toca `~/.codex`. `install.sh` admite `ANTIGRAVITY_SKILLS_DIR`, `CLAUDE_SKILLS_DIR`, `OPENCODE_SKILLS_DIR`, `PI_SKILLS_DIR`, `PI_EXTENSIONS_DIR`, `PI_THEMES_DIR`, `CODEX_SKILLS_DIR` y `CODEX_CONFIG_FILE`; son rutas, no secretos.

CI: GitHub Actions (`.github/workflows/ci.yml`) corre en push a `main` y en todo PR, con ocho jobs: `shell` (`bash -n` + `shellcheck`, bloqueante), `frontmatter` (bloqueante), `version` (`scripts/version.sh`: `VERSION` y manifests sincronizados siempre, salto semver desde el base en PRs; bloqueante en el workflow, y en GitHub recien cuando se sume a los required checks de `main`), `tests` (Node 26 + Pi 0.85.1 + suite completa, bloqueante), `harness-gate` (bloqueante), `plugin-validate` (`claude plugin validate .` sin `--strict`, bloqueante ante errores; es estatico y no requiere autenticacion ni secret), `drift` (informativo) y `release` (solo en push a `main`, despues de los seis jobs bloqueantes: `scripts/version.sh plan-release` decide y `gh release create --generate-notes` crea el tag `v<VERSION>` y su release; un re-run sobre el commit ya tageado no hace nada y un push sin subir `VERSION` falla). Todo es reproducible localmente, incluido `shellcheck` (instalado con `brew install shellcheck`).

Node: la compatibilidad de versiones se verifico a mano el 2026-08-16 en Node `22.18.0`, `22.23.2` (LTS Jod), `24.19.0` (LTS Krypton) y `26.4.0` (entonces con 202/202 tests; hoy la suite completa da 490 tests (ver fila `tests de extensiones`; 450 era el conteo tras retirar `sdd-review-loop` y `wait-pr` en el PR #81) tras sumar el gate `agents-gate` (PR #43), los gates de flujo sin fricción (PR #46), la extension `subagent` con su gate (issue #44), el gate `chiche-land-gate` (issue #66), los tests de loop rojo, riesgo de merge y smells (PRs #69 y #70) y el gate `design-gate` (issue #74) — ver fila `tests de extensiones` — pero no se re-verifico multi-version en cada corrida posterior), usando binarios oficiales descartables de nodejs.org sin tocar el PATH. Node `22.17.1` y `20.20.2` entonces fallaban los 38 archivos con `ERR_UNKNOWN_FILE_EXTENSION: ".ts"` — el type stripping nativo sin flag llega recien en 22.18.0. Para repetirlo: bajar `node-vX.Y.Z-darwin-arm64.tar.gz`, descomprimir en un temporal y correr `<tmp>/bin/node --test pi-extensions/*/*.test.ts` desde la raiz.

Git: branch default `main`, remote `origin` en `ssh://git@github.com/chichex/skills.git`. GitHub CLI esta autenticado con capacidad de PR (verificado 2026-08-15). `/skill:chiche-run` ramifica desde `origin/main`, pushea solo su branch de trabajo y nunca mergea.

## Verificacion autonoma
1. **Estatica basica:** `bash -n`, `git diff --check` y `bash scripts/lint-frontmatter.sh` detectan shell invalido, whitespace y frontmatter incorrecto.
2. **Unitaria determinista:** `node --test pi-extensions/*/*.test.ts`; el glob captura toda logica pura y los gates de doctrina/artefactos.
3. **Gate determinista del plugin de Codex:** `node --test pi-extensions/codex-plugin-gate/codex-plugin-gate.test.ts` valida manifests, separación de harnesses e inventario publicable.
4. **Smoke aislado del plugin de Codex:** con `CODEX_HOME` temporal, `codex plugin marketplace add <checkout>`, `codex plugin list --json --available` y `codex plugin add chiche@chichex` deben resolver la version del manifest y cachear los 14 skills de `codex/` (los 10 de siempre mas los 4 alias deprecados `sdd-*`); verificado el 2026-11-01 con Codex 0.163.0 y `chiche` 3.0.0 (esa version exige `--json` junto con `--available`).
5. **Gate determinista del package:** `node --test pi-extensions/pi-package/pi-package.test.ts` compara el manifest contra el arbol real (via `git ls-files`, no el working tree) y prueba metadata no publicable, peers derivados de los imports reales de codigo trackeado, 14 skills (10 mas los 4 alias deprecados `sdd-*`), 11 factories y un theme. Sus autotests demuestran diagnosticos ante drift, metadata debilitada, imports externos sin peer declarado, y estilos de default-export mas alla de `export default function`.
6. **Carga y lifecycle aislados:** el mismo gate ejecuta `pi -e ./`, RPC `get_commands`, smoke del theme y `pi install/list/remove` con `HOME` y `PI_CODING_AGENT_DIR` temporales; no inicia provider ni persiste sesiones. El smoke legacy carga entrypoints explicitamente.
7. **Fuente Git publicada:** una branch publicada puede probarse con `pi -e git:github.com/chichex/skills@<ref>` y configuracion temporal. Es señal MEDIA por depender de red/GitHub; timeout o fallo de clon queda inconcluso.
8. **CI remota:** replica la estatica/suite, instala Pi 0.85.1 para los probes, agrega `shellcheck` e instala Claude Code 2.1.294 para correr `claude plugin validate .`.
9. **Prueba humana:** TUI, uso real de tools/comandos, seleccion visual del theme, rollout o limpieza del home real, providers y el lifecycle exacto contra `main` post-merge requieren autorizacion o prueba humana.

El techo autonomo es gate determinista mas carga/lifecycle aislados y, cuando hay red, smoke de la fuente Git publicada. No usar la configuracion Pi real ni providers para alcanzarlo.

## Limites
- No ejecutar deploy, publish, `npm publish`, migraciones sobre datos compartidos ni tocar servicios pagos sin confirmacion humana.
- No hacer `git push` a `main`, force-push ni mergear PRs, salvo `/chiche-land` invocado por el humano, que confirma el plan antes de mergear.
- No ejecutar `./install.sh`, `pi install`, `pi remove` ni `pi-clean --confirm` contra el home/configuracion real sin autorizacion separada; usar siempre destinos temporales para pruebas autonomas.
- No activar un theme ni modificar settings reales del usuario durante smokes.
- No modificar ni borrar recursos globales ajenos; la limpieza legacy solo puede apuntar a nombres administrados por este repo.
- No descartar, pisar ni incluir cambios locales preexistentes del usuario.
- No provocar consumo de providers ni errores pagos solo para probar fallback.

## Gaps
- `gh stack` (extension `github/gh-stack`, v0.2.0 del 2026-10-02, GA de stacks 2026-10-06) se tomo del README de `github/gh-stack` (leido via la API de GitHub el 2026-10-08) y de las notas del grill. `gh stack` ya se ejecuto en vivo: merge atómico, `unstack --local` y `branch -d` en `pramaestudio/platform#59/#60` (los dos PRs comparten el merge `896153e`, verificado con `gh pr view` el 2026-10-09), y ahi `gh stack view --json` tenia un head viejo, asi que GitHub sigue mandando sobre el estado local. `sync`, `rebase` y `link` no tienen corrida en vivo registrada en este contrato: su conducta real sigue siendo la prueba humana CA-26 de la spec #66. El piso `gh` >= 2.90.0 es de esa spec (inferencia #9); el README de gh-stack declara `gh` >= 2.0 y Git >= 2.36. Mientras `## Limites` prohiba el force-push, un restack de `gh stack sync`/`rebase` (que aplica `--force-with-lease` sobre `sdd/<slug>/*`) en este repo necesita autorizacion humana explicita.
- El filtro de checks de `chiche-land` (spec #84, CA-1) no distingue el evento de cada run: un workflow que corre en `push` y en `pull_request` sobre el mismo SHA produce dos checks con la misma identidad `workflowName / name`, y el más reciente tapa al otro porque el rollup de `gh` no expone el evento. Limitación aceptada; un `SKIPPED`/`NEUTRAL` posterior y los empates de `startedAt` ya se resuelven hacia el lado conservador.
- `chiche-land` no registra `land.merged` de un PR que quedo `en cola` al vencer `--wait` y que la cola mergeo despues: reanudar no lo recupera (un PR ya `MERGED` no es target de la Fase 3) y `events-v1` no hace backfill. Perdida aceptada en el review de #95; un consumidor puede completar esos merges con `mergedAt` de GitHub.
- Pi 0.85.1 es la version contractual probada, no una version minima declarada del package.
- La tool `subagent` bloquea el anidamiento: el hijo hereda `PI_SUBAGENT_DEPTH=1` y la tool rechaza lanzar desde un proceso con esa marca. Un `pi` interactivo abierto a mano desde un hijo tambien queda bloqueado; aceptable y documentado.
- Los jobs de `subagent` viven en memoria por sesion: `/new` y `/reload` disparan `session_shutdown`, que mata los hijos vivos (SIGTERM, SIGKILL a los 5 s) y avisa cuales aborto; un run en curso se pierde y no hay persistencia de resultados fuera de la sesion.
- `--tools` filtra tambien las tools de extension: `reviewer` y `scout` (`tools: read, grep, find, ls, bash`) no ven `ask_user_question`, `subagent` ni `persist_sdd_spec`. Es deseado; `implementer` no declara `tools` y hereda todas.
- `pi-extensions/subagent/` vendoriza y adapta el ejemplo `examples/extensions/subagent` de Pi 0.85.1: cambios futuros del ejemplo upstream no llegan solos. La conducta real en TUI (background, `subagent-result`, `/subagents abort`, kill al cerrar) queda como prueba humana: exige provider y sesion interactiva. Lo mismo vale para el corte por timeout con provider real (un scout que vence en una sesion interactiva, con salida parcial y `failed (timeout)`/`Agent timeout` visibles al modelo): el gate solo lo prueba con hijo simulado.
- `engines.node` declara `>=22.19.0` alineado con el engine de `@earendil-works/pi-coding-agent`; el piso propio del repo es 22.18.0 (type stripping nativo sin flag). CI corre solo Node 26, asi que la compatibilidad con 22.x/24.x no tiene gate automatizado — se verifico a mano (ver `## Ambientes`) y puede driftear.
- No hay typecheck, lint TypeScript, coverage ni build automatizado.
- No hay e2e automatizado para TUI, cambio de modelo, compactacion ni fallback de provider. La conducta emergente de agentes siguiendo skills la cubre parcialmente la suite `evals/` de `claude plugin eval` (triggering de `chiche-init`, `chiche-spec`, `chiche-run` y `grill`, y adherencia de `chiche-spec`): es paga, no determinista y corre solo a demanda (local o `plugin-eval.yml`), nunca en el CI de cada PR. Los otros 5 skills de `claude/` (`coding-policies`, `design-system`, `issue-triage`, `chiche-land`, `tdd`) y la adherencia de `chiche-run` no tienen casos.
- Los smokes Git dependen de red/GitHub; un fallo de infraestructura no prueba un defecto del package.
- El manifest declara `pi.skills`/`pi.themes` a nivel de directorio completo (`./pi`, `./pi-themes`), no archivo por archivo como `pi.extensions`; el gate compensa con `EXPECTED_SKILLS`/`EXPECTED_THEMES` hardcodeados como unico punto de aprobacion explicita para altas/bajas de skills y themes. Colapsar esa capa (como se hizo para extensiones) exigiria cambiar el shape del manifest y no esta confirmado que Pi soporte listas por archivo ahi — queda como propuesta, no implementado.
- La deteccion de "el Pi Package nativo ya esta instalado" en `install.sh` (`pi_native_package_conflict`) usa `pi list` y matchea el literal `chichex/skills`, el literal `chichex/chiche` (el nombre del repo tras el renombre del issue #103) o el path absoluto de este checkout; un fork con otro nombre de repo, o el mismo repo clonado en OTRA ruta e instalado ahi via path local, no se detectan.
